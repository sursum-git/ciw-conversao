# Revisão do candidato de download

O produto acrescenta somente download autenticado ao op1004 existente. Consulta/lista antiga continuam no mesmo leitor; GET de referência novo usa anexos-arquivo e resolve o mesmo mestre/filho por CID+PK, exigindo cod-estabel prefixo5 antes de acessar qualquer filho/referência. Não cria tela, tabela, código operacional, fórmula, sequência ou writer. Campos anteriores da entidade e do programa foram preservados dos exports vivos; código de manutenção não foi habilitado.

Fontes: cons_anexos_container_grid.class.php3976–4003 protege na sessão o nome persistido antes do doc.php; form_anexos_container_apl.php3833–3846 e5436–5442 grava basename de upload no path_doc; index.php47/103/421/729 resolve _lib/file/doc. O subdiretório do link é vazio. O doc.php específico não está na coleta atual; não se afirma paridade literal de sua entrega HTTP nem autorização operacional antiga. A configuração real do root do broker para esses arquivos exige preflight readonly do root antes da ativação; nenhum path foi inventado.

Schema local de anexos tem7campos e PK anexo_container_id; tipos_anexo e pp-container também conferidos. GET novo retorna esses7campos, dois metadados existentes e cod_estabel do mestre como prova interna; mapper não expõe esse comprovante. NULL/vazio/espaços e strings históricas são preservados. Aliases/clientes sem contexto, strings numéricas, extras, PK conflitante ou outro container são recusados. O recurso não aceita read, escrita ou upload. É um lookup único por PK física; não acrescenta varredura, paginação ou altera os limites/lista do painel legado.

Runtime executa read/get/download reais nos testes, com mocks somente de transporte/repositório. O adapter verifica source/binding fixos, IDs/contexto, shape raw e MED antes do mapper/storage. Download usa usuário da sessão, permissão container_anexos_progress.read e owner derivado dos IDs retornados; qualquer nome ecoado pelo navegador é ignorado. Sem resposta raw válida, não há chamada storage nem log de sucesso. Logs de consulta permanecem técnicos; não são fabricados audit ou before/after de negócio.

BinaryFileResponse, Client/Broker/FilePolicy e RuntimeFileTransferContext são os existentes, sem modificações. Política histórica conserva nomes, extensão e tamanho anteriores; o teste com broker real local aceita .historico.exe de20MB+1 e rejeita paths/URL/NUL. Arquivos de teste são novos e temporários, removidos ao fim; nada acessa documento real. Bytes baixados são descartados pelo ciclo existente de resposta/contexto, sem tocar o arquivo de origem.

Builder usa o perfil novo fechado para registrar attachments.download com .read e campo file readonly; perfil antigo sem a nova operação mantém seu mapa. Editor writable foi recusado em teste. A fonte11 inteira passa pelo normalizador real, conservando type detail; prova complementar da fonte134 de1051 também confirma detail, sem alterar seu freeze. NativeKendo+AJV exercitam grade/get/view/botão, payload CID+PK, upload desabilitado/sem registro e blob revogado em memória. O frontend/Kendo não foi alterado. Limitação visual herdada: o file editor readonly ainda exibe a dica de upload20MB e picker desabilitado; essa dica não é uma restrição de download. Não afirmar paridade visual literal nem teto histórico20MB.

Os três patches de produção são byte-exatos, com oldBytesHex/newBytesHex e SHA físicos; todos os bytes fora dos anchors, inclusive LF preexistentes mistos, são preservados e reversíveis ao baseline. Não usar read_text/write_text universal para compor arquivos compartilhados. Fonte/entity/programa são deltas específicos sobre snapshots vivos; nunca reaplicar DTO sanitizado para autenticação. Integração/compilação12.2/.42/publicação/validação real somente pelo root em sursum-api/med. Nenhuma escrita comercial, grant, SSH ou DDL executado.
